# 레이트 리밋 — 탐지·차단과 비교 (2026-11-22)

nginx 에 출발지별 레이트 리밋(`limit_req`)을 넣고, 기존 탐지·자동 차단(Sigma 룰 + ML)과 **따로 · 같이** 켜서 같은 공격을 채점했다.
질문은 하나다: **레이트 리밋만으로 충분한가, ML 은 무엇을 더 하나.**

## 결론

- **빠른 BOLA(초당 약 2.5건):** 레이트 리밋만으로도 새어 나간 주문이 탐지·차단만 켠 것과 비슷했다 (16 vs 18). 다만 **막은 게 아니라 늦춘 것**이다. 공격자는 429 를 받으면서도 분당 30건씩 계속 가져간다. 이 실험의 숫자가 작은 건 공격 스크립트가 150건에서 멈추기 때문이다.
- **느린 BOLA(2.5초 간격 = 제한 아래):** 레이트 리밋은 **한 건도 못 막았다** (429 0건 · 40건 전부 유출). 탐지·차단을 같이 켜면 ML 이 32초 만에 막아 14건.
- **정상 사용자 20명은 어느 조건에서도 429 를 받지 않았다** (분당 30 · burst 10 설정 기준). 오탐 차단도 전 조건 0.
- 그래서 둘은 역할이 다르다: 레이트 리밋 = **양의 상한** (빠른 자동화의 속도를 깎음), ML = **행위 판정** (느리게 해도 "남의 주문을 순서대로 훑는다"는 모양을 봄). 레이트 리밋은 기본으로 켜고, 그 아래로 숨는 공격을 탐지가 맡는다.

## 설정

| 항목 | 값 |
|---|---|
| 레이트 리밋 | `limit_req_zone $client rate=30r/m` (0.5 req/s) · `burst=10 nodelay` · 넘치면 **429** |
| 키 | `$client` = `X-Client-IP` 헤더 (차단 목록과 같은 키) |
| 순서 | 차단 목록(403, rewrite 단계) → 레이트 리밋(429, preaccess 단계) → DVRA |
| 정상 사용자 | 20명, 약 20초마다 2~6건 몰아서 → burst 10 안, 평균 약 0.2 req/s |
| 빠른 BOLA | `traffic demo` 안의 BOLA: 남의 주문 1..150, 0.4초 간격 |
| 느린 BOLA | `traffic attack bola --delay 2.5` (0.4 req/s), 정상 20명과 같이 |
| 탐지·차단 | 기본값 (룰 L3 · F1 · F2 · ML high + 창 15건 이상 → 차단) |
| "탐지만" 조건 | `LAB_BLOCK_GROUPS=none LAB_BLOCK_MIN_REQ=999999` — 탐지는 기록하되 차단은 안 함 |

켜는 법은 [README 설정 표](../README.md#기본-탐지와-차단-정책)의 `LAB_RATE` · `LAB_BURST`.

### 읽는 법

- **B:** BOLA 152건 중 111건이 429. 통과한 41건 중 2xx(남의 주문) 16건. 공격이 60초 동안만 돌아서 이 정도다 — 10분 돌면 burst 10 + 분당 30건이 계속 통과한다. 레이트 리밋만으로는 **끝이 없다**.
- **C:** ML 이 6.2초에 막았다. 그때까지 BOLA 는 13건을 보냈고 (주문 14부터 403) burst(10)가 막 바닥난 참이라 429 는 2건뿐. 빠른 공격에서는 **차단이 레이트 리밋보다 먼저 일한다**. A 와 C 의 차이(18 → 11)는 한 번씩이라 레이트 리밋 효과라고 말하기 어렵다 — 같은 PC 에서 A 설정 다섯 번의 유출이 16~22였다 (README "기본 설정 결과").
- **D:** 레이트 리밋 아래로 오면 429 가 0. 탐지(ML)는 14.2초에 했지만 차단을 끈 조건이라 150건 전부 응답 — 유출 40 = 존재하는 남의 주문 전부.
- **E:** 느린 공격은 ML 탐지도 늦다 (18초, 빠른 공격은 2~4초). 차단까지 32초는 대부분 **차단 정책의 "창 요청 15건 이상"** 때문이다: 2.5초 × 15건 ≈ 37초. 즉 E 의 유출 14건은 모델이 아니라 이 정책 값이 정한 하한에 가깝다.
- **probe(숨은 API 탐색):** 15곳 · 17건이라 레이트 리밋과 상관없이 룰 L3 로 막혔다 (B 에서 429 3건). 유출 2 = `/debug` · `/delivery/orders` 첫 응답.

## 1회차는 무효였다 — compose 가 nginx 를 다시 만듦

처음 돌린 실험(원본은 [`raw/invalid_run1/`](results/rate-limit_2026-11-22/raw/invalid_run1/))은 B~E 전부 429 가 0건이었다. 원인:

```
LAB_RATE=30r/m docker compose up -d       # nginx 가 레이트 리밋을 켜고 뜸
docker compose run --rm traffic demo      # ← 이 명령엔 LAB_RATE 가 없다
  Container nginx-1 Recreate              # compose 가 설정이 달라졌다고 보고 nginx 를 env 없이 다시 만듦
```

`compose run` 은 의존 서비스(traffic → nginx)를 **그 명령의 env 로 다시 계산**한다. 그래서 레이트 리밋이 조용히 꺼졌다. 탐지 쪽 설정(`LAB_BLOCK_*`)은 traffic 의 의존이 아니라서 살아남아, 겉보기엔 실험이 제대로 돈 것처럼 보였다.
고친 것: `run.sh` 가 조건마다 env 를 `export` 하고, 끝날 때 nginx 로그의 "레이트 리밋 켬" 줄과 재생성 여부를 출력한다. 쓰는 사람도 같은 함정에 빠지므로 **`LAB_RATE` 는 `export` 하거나 `.env` 에 적으라**고 README 에 적었다.
A(레이트 리밋 없음)는 이 문제와 무관해 1회차 결과를 그대로 썼다.

## 한계

- **조건마다 한 번씩**이다. 시간 · 유출 수는 실행마다 흔들린다 (A 설정 다섯 번: BOLA 유출 16~22). "B ≈ A", "C 가 조금 낮다"는 이 범위 안의 차이다. 확실한 결론은 D vs E (40 vs 14, 429 0건) 와 B 의 429 111건 쪽이다.
- **키가 `X-Client-IP` 헤더**다. 연습장에서 출발지를 흉내 내려고 쓰는 헤더라 위조할 수 있다 — 요청마다 값을 바꾸면 레이트 리밋도 차단 목록도 무력하다. 실제 환경이면 TCP 출발지 주소나 인증된 사용자 ID(토큰)로 키를 잡아야 하고, BOLA 는 **사용자 ID 키**가 더 맞다 (IP 를 바꿔도 계정은 하나).
- 값(분당 30 · burst 10)은 이 연습장의 **합성 정상 트래픽**에 맞춘 것이다. 실제 서비스는 정상 사용자의 최대 속도를 로그에서 먼저 재고 정해야 한다.
- 레이트 리밋은 nginx 하나에서만 셈한다 (메모리 zone). 서버가 여러 대면 공유 저장소가 필요하다.
- BOLA 자체의 근본 해결은 앱의 **객체 권한 검사**다. 레이트 리밋과 탐지는 그게 빠졌을 때의 피해를 줄이는 층이다.
